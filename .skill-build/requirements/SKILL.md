# Requirements Processor

요구사항 파일을 읽어 공통 규칙을 적용한 코드 구현 계획을 작성한다.

---

## ⚙️ 공통 규칙 (이 섹션을 직접 수정해 운영 방침을 조정하세요)

### 제한 사항 (Restrictions)
- **refactoring 금지**: 요청된 기능 구현에만 집중한다. 기존 코드의 구조·네이밍·스타일을 리팩토링하지 않는다.
- **범위 초과 금지**: 요구사항에 명시되지 않은 기능을 임의로 추가하지 않는다.
- **파일 생성 최소화**: 새 파일은 꼭 필요한 경우에만 만든다. 기존 파일 수정을 우선한다.

### 추가 제안 (Suggestions)
- **enabled: true** — 구현 계획 마지막에 선택적 개선 아이디어를 제안한다.
  (비활성화하려면 `enabled: false`로 변경)

---

## 처리 흐름

1. **파일 읽기**: 사용자가 제시한 `.md` 파일을 읽는다.
2. **요구사항 파악**: 구현해야 할 기능·변경사항을 정리한다.
3. **코드베이스 탐색**: 영향받는 파일·컴포넌트·API를 파악한다. 관련 파일을 직접 읽어 현재 구조를 확인한다.
4. **계획 작성**: 아래 출력 형식에 따라 태스크 목록을 작성한다.
5. **규칙 적용 확인**: 제한 사항을 위반하는 항목이 없는지 검토한다.
6. **추가 제안**: `Suggestions.enabled`가 true이면 선택적 개선 아이디어를 마지막에 덧붙인다.

---

## 출력 형식

```
## 구현 계획: [요구사항 제목 또는 파일명]

### 요구사항 요약
- (한 줄씩 핵심 요구사항 나열)

### 구현 태스크

1. **[태스크명]**
   - 파일: `경로/파일명`
   - 작업: 무엇을 어떻게 변경하는지 (1~3줄)
   - 의존: 선행 태스크 번호 (없으면 생략)

2. **[태스크명]**
   ...

### 적용된 제한 사항
- ✓ 리팩토링 없음 (기존 코드 구조 유지)
- ✓ 요구사항 범위 내 구현

### 💡 추가 제안 (선택 사항)
- (고려할 수 있는 개선 아이디어, Suggestions.enabled=false 시 생략)
```

---

## 주의사항

- 태스크 번호는 구현 순서를 반영한다. 의존 관계가 있는 경우 먼저 처리해야 하는 태스크를 앞에 둔다.
- 파일 경로는 프로젝트 루트 기준 상대 경로로 표기한다.
- 이미 구현된 내용은 태스크에 포함하지 않는다. 코드베이스를 확인한 뒤 실제로 필요한 변경만 나열한다.
- 요구사항이 불명확한 부분은 계획에 `[❓ 확인 필요: ...]` 로 표시한다.
